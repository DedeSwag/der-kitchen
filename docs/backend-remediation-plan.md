# 陈哥厨房后端整改顺序（Sa-Token 基线版）

> 更新日期：2026-08-08
> 前提：项目未上线，不保留历史数据库迁移兼容，不迁移历史数据。
> 目标：先建立稳定的身份与数据基线，再按业务闭环逐域完成实现和测试。

## 一、已确定的技术决策

- 认证框架采用 Sa-Token 1.45.0，使用标准有状态会话，不使用 Sa-Token JWT 插件。
- 小程序微信登录和管理端账号密码登录共用 `sys_user` 账号体系。
- token 继续通过 `Authorization: Bearer <token>` 传递，前端协议无需改变。
- 管理员身份由独立的 `admin-openids` 配置或数据库账号角色确定，不再按白名单顺序推断。
- 单实例开发阶段使用 Sa-Token 默认内存会话。服务重启后 token 失效是当前明确接受的行为。
- 需要多实例部署或要求会话跨重启保留时，再增加 Redis 持久层；当前不提前引入运维复杂度。
- 管理端密码继续使用 BCrypt，不在 token 中存放角色、昵称等可变业务数据。

## 二、调整后的处理顺序

### 1. 鉴权基线（已完成）

- 引入 `sa-token-spring-boot3-starter`。
- 两个登录入口建立 Sa-Token 会话，补齐退出登录和改密后全端下线。
- `/api/**` 默认要求登录，仅放行微信登录和管理端登录。
- `/api/v1/admin/**`、`/api/common/file/**` 统一要求 `admin` 角色。
- 角色从 `sys_user` 实时读取；禁用账号在请求入口再次拦截。
- 删除自研 JWT、JWT Filter、`UserContextHolder`、`@RequireRole` 和角色 AOP。
- 当前用户统一从 `SecurityUtils` 获取。

这样调整到第一步，是因为后续所有用户数据隔离、管理员操作、审计字段和接口测试都依赖稳定的登录用户标识。

### 2. 数据库单一基线（已完成）

- 以最终需求和实体/Mapper 为准重新设计一份干净的 `V1__init.sql`。
- 不再保留当前 V1 → V2 → V3 的补丁链；删除重复建表、改名和兼容性 SQL。
- 逐表核对表名、字段名、类型、默认值、唯一约束、外键、索引、逻辑删除和审计字段。
- 重点统一 `sys_user`、分类、菜品、文件、订单、订单明细、收藏及通知相关表。
- 明确接入 Flyway，由应用启动负责迁移；Docker 只负责提供 PostgreSQL，不再让容器初始化脚本和应用迁移形成双入口。
- 增加 PostgreSQL/Testcontainers 迁移测试，验证空库可以一次建成且 Mapper 基本读写成立。

完成结果：Flyway 已在空 PostgreSQL 15 上成功执行唯一 V1，最终七张表和核心 Mapper 读写均由 Testcontainers 验证通过。详细约束见 [database-baseline.md](./database-baseline.md)。

### 3. 模块边界和通用基础设施收口（已完成）

- 固化 `app → common + file`、`file → common` 的单向 Maven 依赖。
- 清理残留的旧包结构、重复配置和无效依赖。
- 统一异常码与 HTTP 状态语义，完善参数校验和敏感字段脱敏。
- 检查 CORS、Swagger/Actuator 暴露范围、环境变量及日志脱敏。
- 为鉴权矩阵补集成测试：未登录 401、普通用户访问管理端 403、禁用账号拒绝访问、退出和改密后 token 失效。

完成结果：各模块只声明自身直接依赖，底层模块不再向 app 隐式泄漏框架运行时；HTTP 状态、参数校验、CORS、OpenAPI、Actuator、日志与外部服务异常已统一。鉴权矩阵和订单归属通过 PostgreSQL/Testcontainers + MockMvc 集成测试覆盖。用户订单详情的横向越权、批量操作事务性以及点菜可用性校验也已在本阶段闭环。详细约定见 [backend-infrastructure.md](./backend-infrastructure.md)。

### 4. 分类、菜品、文件、收藏闭环（已完成）

- 分类与菜品上下架、状态、排序和删除约束保持一致。
- 明确菜品图片只保存 `fileId`/对象键还是 URL，避免数据库存储短期预签名 URL。
- 文件上传校验真实文件类型、大小、归属和删除引用约束。
- 收藏增加菜品存在性、可见性和唯一约束校验。
- 每个域完成 Service 单元测试和 Controller 集成测试后再进入订单域。

完成结果：分类显示状态已成为用户端菜品和收藏的统一可见性边界；菜品状态、上下架、软删除、唯一名称和历史订单快照行为已验证。菜品只持久化 `image_file_id`，请求提交 `imageFileId`，短期 URL 仅在响应时生成。文件上传验证真实签名、可解析内容、尺寸、大小和归属，被菜品引用时禁止删除；上传与删除已在真实 MinIO 上验证。收藏列表返回完整菜品 VO，并以 PostgreSQL `ON CONFLICT DO NOTHING` 保证重复收藏幂等。详细约定见 [category-dish-file-favorite.md](./category-dish-file-favorite.md)。

### 5. 订单核心闭环

- 把允许的状态迁移固化为唯一状态机，用户端和管理端共用同一规则。
- 创建订单时生成菜品名称等必要快照，避免菜品修改影响历史订单含义。
- 所有订单详情、取消和加菜接口校验订单归属，消除越权读取或修改。
- 明确加菜对订单金额、明细和状态的原子更新，并补事务与并发保护。

完成结果：订单创建在写入前完成预约日期、重复菜品及全部菜品可点性校验，订单明细保存菜名快照；用户与管理员共用 `OrderStatus` 唯一迁移规则。取消、加菜和状态流转按订单主记录加行锁并在事务内执行，归属、终态和并发冲突均有明确 HTTP 语义。订单列表现已返回菜品摘要，前后端统一为 `mealDate + mealType`、标准备注字段和 `/status` 状态接口。当前产品没有价格模型，因此本阶段不存在金额更新；后续若引入定价，需同时增加金额快照。详细约定见 [order-core.md](./order-core.md)。
- 用集成测试覆盖创建、查询、取消、接单、制作、完成及非法迁移。

### 6. 通知与待办闭环（已完成）

- 根据需求确定站内通知/订阅消息的数据模型和触发点。
- 订单事件与通知落库放在一致的事务边界，外部微信消息使用可重试的异步投递。
- 管理端待处理数量与订单状态使用同一口径。

完成结果：新增 `biz_order_event` 和 `sys_notification`，创建订单、加菜、用户取消及管理端状态流转全部持久化事件；前三类用户动作生成管理员站内通知。事件和通知强制加入订单事务，微信仅消费持久化待投递记录。异步任务采用跳过锁定的原子领取、超时恢复、指数退避、最大次数和终态保护；管理员小程序提供一次性订阅授权入口。管理端与小程序按 `afterId` 增量轮询通知，待接单数严格复用 `pending` 状态口径。

### 7. 统计重写（已完成）

- 在最终表结构和订单状态口径稳定后再改统计 SQL。
- 清除所有旧表名引用，统一日期边界、取消订单过滤和金额计算口径。
- 为概览、热门菜品和每日汇总准备固定数据集的查询测试。

完成结果：统计 SQL 只引用最终表，统一上海业务日期、闭区间和取消订单过滤；概览、热门菜品、每日汇总都返回强类型 VO。热门菜品按 `dishId` 聚合数量并读取最新订单快照名，每日汇总补齐零数据日期，查询范围限制为最多 366 天。当前模型没有价格字段，因此明确不提供虚假金额口径。固定数据集已通过真实 PostgreSQL 测试。

### 8. 契约联调与交付基线

- 对照需求文档、管理端和小程序的实际调用，统一路径、字段、分页和错误码。（已完成）
- 生成并校验 OpenAPI 文档，补充关键端到端用例。
- 完成全量测试、镜像构建、空环境部署演练、健康检查和配置清单。

第一项完成结果：接口统一使用 `/api/v1`（文件接口为 `/api/common/file`）、扁平登录结构、`pageNum/pageSize` 请求与 `records/total/pageNum/pageSize` 响应；实体不再直接出参，菜品图片写字段固定为 `imageFileId`。HTTP 状态与响应体 `code` 同值，双端请求层保留真实错误码。完整基线见 [notification-stats-api-contract.md](./notification-stats-api-contract.md)。阶段 8 的 OpenAPI 校验与完整交付演练仍作为后续任务。

## 三、阶段门禁

每一阶段都必须同时满足：代码编译通过、自动化测试通过、文档与实现一致、无旧命名/旧鉴权残留。数据库基线已经锁定，后续结构变化在首次部署前直接修订 V1；首次部署后只允许新增前向迁移。
