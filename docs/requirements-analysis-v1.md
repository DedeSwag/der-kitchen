## 一、项目概述

### 1.1 项目背景

日常家庭做饭场景中，夫妻间"吃什么"的沟通成本高，口头传达容易遗漏忌口、口味偏好等信息。本项目旨在打造一款极简私密的家庭点菜小程序，实现老婆线上点菜、陈哥后台管理的闭环流程。

### 1.2 项目目标

- 替代口头沟通，结构化记录点餐需求，提升家庭做菜趣味
- 老婆零学习成本完成点菜操作
- 陈哥高效管理菜品和订单
- 架构预留二期多用户扩展能力

### 1.3 用户角色

| 角色 | 用户 | 权限范围 |
|------|------|----------|
| 普通用户 | 老婆（一期唯一） | 浏览菜品、点菜下单、查看进度、收藏菜品 |
| 管理员 | 陈哥 | 菜品管理、订单管理、数据统计、权限管理 |

## 二、功能模块拆解

### 2.1 用户端（小程序）

#### 2.1.1 菜品浏览模块

**功能点：**

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| U-B-01 | 分类展示 | 按管理员自定义分类展示菜品列表（家常菜、汤羹、主食、小吃、专属私房菜等） | P0 |
| U-B-02 | 菜品详情 | 展示菜品实拍图片、简单文字介绍 | P0 |
| U-B-03 | 菜品状态标识 | 展示菜品当前状态（可点/缺货/暂不做），缺货菜品置灰不可选 | P0 |
| U-B-04 | 收藏菜品 | 一键收藏/取消收藏，收藏列表可快速复点 | P1 |

**业务规则：**
- 仅展示"已上架"菜品
- 缺货/暂不做菜品展示但不可加入订单
- 分类顺序由管理员后台配置

#### 2.1.2 点菜下单模块

**功能点：**

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| U-O-01 | 选菜加购 | 从菜品列表/收藏列表选择菜品，支持增减数量 | P0 |
| U-O-02 | 口味备注 | 下单时可选择预设口味标签（微辣/不辣/少油少盐）+ 自由文本备注 | P0 |
| U-O-03 | 忌口说明 | 支持填写忌口信息（如：不要香菜、不要葱等） | P0 |
| U-O-04 | 特殊要求 | 自由文本输入特殊烹饪要求（多汤汁、软烂等） | P1 |
| U-O-05 | 预约点餐 | 选择用餐时段：当日晚餐、次日早/午/晚餐 | P0 |
| U-O-06 | 一键下单 | 确认菜品和备注后提交订单 | P0 |
| U-O-07 | 临时加菜 | 已下单后可追加菜品到当前订单 | P1 |
| U-O-08 | 撤销订单 | 订单状态为"待接单"时可撤销 | P1 |
| U-O-09 | 历史订单复刻 | 从历史订单中一键复制菜品到新订单 | P1 |

**业务规则：**
- 每个订单必须关联一个用餐时段
- 仅"待接单"状态的订单可撤销
- 加菜操作生成追加记录，归属同一订单
- 预约点餐最多提前1天

#### 2.1.3 订单进度模块

**功能点：**

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| U-P-01 | 实时状态 | 展示订单当前状态：待接单 → 备菜中 → 烹饪中 → 已完成 | P0 |
| U-P-02 | 历史记录 | 按时间倒序展示所有历史订单 | P0 |
| U-P-03 | 订单详情 | 查看订单菜品明细、备注、时间等 | P0 |

**订单状态流转：**

```
待接单 → 备菜中 → 烹饪中 → 已完成
  ↓                              
已取消（管理员/用户撤销）
```

#### 2.1.4 个人中心模块

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| U-M-01 | 我的收藏 | 收藏菜品列表，支持取消收藏和快速下单 | P1 |
| U-M-02 | 我的订单 | 订单列表入口（同订单进度模块） | P0 |

### 2.2 管理端（Web 端主力 + 小程序轻量接单）

> **平台决策说明：**
> 管理端采用「Web 电脑端为主、小程序内嵌简版为辅」的双端策略。
> - **Web 电脑端**：承载菜品管理、分类管理、数据统计等低频但操作复杂的功能，大屏操作效率高、图片上传体验好。
> - **小程序管理页（嵌入同一小程序）**：仅提供轻量接单页，陈哥在厨房做饭时无需开电脑，手机即可完成接单、推进订单状态、查看备注等高频操作，并通过微信推送实时感知新订单。

#### 2.2.1 菜品管理模块

> 📍 **载体：Web 电脑端**

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| A-D-01 | 新增菜品 | 填写菜名、简介、分类、烹饪时长，上传图片 | P0 |
| A-D-02 | 编辑菜品 | 修改菜品信息 | P0 |
| A-D-03 | 删除菜品 | 软删除菜品（历史订单保留关联） | P1 |
| A-D-04 | 上下架管理 | 控制菜品是否在用户端展示 | P0 |
| A-D-05 | 状态设置 | 设置菜品为正常/缺货/暂不做 | P0 |
| A-D-06 | 分类管理 | 新增/编辑/排序菜品分类 | P0 |

**业务规则：**
- 菜品删除采用软删除，已关联历史订单的菜品不物理删除
- 下架菜品用户端不可见
- 缺货菜品用户端可见但不可点

| A-O-07 | 历史查询 | 查询所有历史订单，支持按日期范围筛选 | P1 |

## 六、非功能性需求

### 6.1 性能要求

- 页面加载时间 < 2秒
- 订单提交响应时间 < 1秒
- 新订单通知延迟 < 5秒

### 6.2 安全性

- 用户通过微信登录鉴权，无需额外注册
- 管理员通过特定标识区分，接口层做角色校验
- 一期不开放注册入口，用户仅通过后台配置

### 6.3 可用性

- 支持微信小程序平台
- 管理端兼容手机和PC浏览器
- 离线时给出明确提示

### 6.4 扩展性设计

- 用户表预留 role 字段和 family_id 字段（二期多成员）
- 订单表预留 merged_order_id 字段（二期合并点餐）
- 数据库设计遵循范式化，便于后续扩展
- 接口版本化（/api/v1/）

## 七、技术选型建议

| 层面 | 推荐方案 | 理由 |
|------|----------|------|
| 用户端框架 | uni-app / Taro（小程序） | 用户点菜主场景，原生小程序体验最佳 |
| 管理端-Web | Vue 3 + Vite（H5/PC浏览器） | 大屏操作效率高，适合菜品管理、数据统计等复杂操作 |
| 管理端-小程序 | uni-app 内嵌管理页 | 与用户端同一小程序，通过角色判断展示接单页，免额外审核 |
| 后端服务 | 微信云开发 / Node.js + 云函数 | 免运维、成本低、适合轻量应用 |
| 数据库 | 云数据库（MongoDB） | 云开发原生支持，无需额外部署 |
| 文件存储 | 云存储 | 菜品图片上传存储 |
| 消息推送 | 微信订阅消息 + 小程序内轮询 | 订阅消息触达管理员；厨房场景补充小程序内铃声+轮询兜底 |

## 十、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 微信订阅消息限制 | 管理员可能错过新订单 | 补充小程序内铃声提醒 + 长连接轮询 |
| 菜品图片上传体验 | 上传慢影响管理效率 | 图片压缩 + 支持从相册快速选取 |
| 一期用户固定 | 无灵活性 | 后台配置白名单openid，二期可扩展 |
